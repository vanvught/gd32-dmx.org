GD32 Pixel Output Engine

Modern, high-performance pixel control for Cortex-ARM

A highly optimized Art-Net and sACN pixel controller for GD32 Cortex-ARM microcontrollers, built around a Timer → DMA → GPIO architecture for deterministic timing, minimal CPU overhead, and maximum output efficiency. This design uses the hardware exactly where Cortex-ARM performs best: timers for precise scheduling, DMA for data movement, and GPIO for direct waveform generation.

Key features

  • No artificial FPS limit beyond what is imposed by the selected pixel chip protocol.
  • Full Art-Net 4 implementation, including ArtTrigger for running test patterns.
  • Full sACN E1.31 implementation.
  • Discovery and network configuration using RDMNet LLRP only.
  • Central remote configuration based on UDP-readable messages.
  • Configuration management with HTTP/JSON, including discovery support.
  • TFTP server support for uploading new firmware.

Supported protocols

  • RTZ protocol pixels, including predefined chip types such as WS2812B. When different timing is needed, it can be configured using custom low-code and high-code values.
  • Clock-based protocol pixels: APA102, SK9822 and P9813.
The implementation is designed to exploit the strengths of Cortex-ARM microcontrollers: precise hardware timing, DMA-driven transfers, and minimal interrupt load.

Core architecture

Timer → DMA → GPIO

The output engine uses two timers in master-slave mode. The master generates the DMA requests and the slave acts as the pixel buffer counter. There is just one interrupt for the transfer lifecycle. This makes the design exceptionally efficient for Cortex-ARM, because the waveform generation is handled by hardware rather than software polling or tight interrupt loops.

Why this architecture is so effective on Cortex-ARM

  • Precise timing is generated by the timer hardware.
  • DMA writes directly to the GPIO set/reset registers.
  • CPU overhead stays low during pixel output.
  • Interrupt pressure is minimized to a single interrupt for the transfer process.
  • Scaling across multiple outputs becomes practical without compromising timing integrity.

RTZ protocol DMA requests

For RTZ protocol pixels there are three DMA requests:

  1. Always the HIGH output.
  2. The LOW output for a 0 code.
  3. Always the LOW output after T1H.

Implementation summary

This is the kind of design that suits Cortex-ARM extremely well: the application prepares the buffer once, then the timer and DMA peripherals take over the real-time work. The result is stable output timing, low jitter, and excellent performance without wasting CPU cycles.

Alternative transport

SPI / I2S

As the SPI speed cannot be specified exactly, the I2S peripheral is used instead. In this design, SPI speed = I2S bitrate = audio sample rate × number of bits per channel × number of channels. Therefore:

Audio sample rate = SPI speed / 16 / 2
For WS2812B-type protocols, the SPI speed must be close to 6.4 MHz.

I2S prescaler configuration

  • Frame format: DT16B CH16B
  • Number of bits per channel: 16
  • Number of channels: 2
  • Audio sample rate: 200 kHz = 6400000 Hz / 16 / 2
  • MCK out: Disable

I2S bitrate = CK_I2S / (DIV × 2 + OF)

This method provides a practical and stable way to generate the required bitstream timing when exact SPI clock selection is not available.
