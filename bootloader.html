Firmware update

Bootloader with TFTP Update Support

The bootloader installs your application over the TFTP protocol, so there is no need to modify your application code. By default it uses DHCP to obtain an IP address, making firmware updates straightforward on supported GD32 targets.

  • TFTP firmware upload
  • No application changes
  • DHCP by default
  • GD32F1 / F2 / F4 / H7
Firmware limits Java update UI

How it works

  • Bootloader receives firmware using TFTP
  • Application code stays unchanged
  • IP addressing uses DHCP by default
  • Activation is controlled during board reset

Practical focus

This bootloader is intended for reliable field updates on embedded GD32 platforms. The upload size limit depends on the available RAM of the target MCU, because the firmware image must fit within the bootloader’s working constraints.

Firmware capacity

Maximum firmware size by MCU

Why there is a limit

The maximum firmware file size that can be uploaded is determined by the amount of RAM available on the target. Larger-memory devices can accommodate larger firmware images during the update process.

Activation

When the bootloader becomes active

Activation conditions

  • During board reset when KEY_BOOTLOADER_TFTP_GPIO_PINx is pressed
  • During board reset when bkp_data_read(BKP_DATA_1) == 0xA5A5

Application-triggered entry

The backup register condition can be set by the running application using human readable UDP messages. This provides a convenient way to request a bootloader restart remotely without changing the firmware update flow.

The bootloader entry mechanism is designed so updates can be initiated either physically on the board or programmatically from the application environment.
